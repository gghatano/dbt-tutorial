# 10-9: (open-ended) ペア (or 将来の自分) の DAG をレビューする

## シナリオ

10-8 で「自分の DAG を他者から読まれる側」 を経験した。本問は **視点反転**: 他者の DAG を読み、レビューコメントを書く側に回る。

レビュー対象は以下のいずれか:

- **ペアの学習者** が書いた `learner/design_review.md` + DAG (一緒に学習している人がいれば)
- **将来の自分** (= 6 ヶ月前の自分の DAG を、今の自分が読み返す)
- **6 ヶ月前の自分** (もし過去の dbt プロジェクトがあるなら)

> **単独学習者向け注記**: ペアがいなくても OK。「6 ヶ月前 / 6 ヶ月後の自分」 はコードレビューの良い練習相手。**他人の頭で書いたつもりで自分の DAG を読む** だけでも、見えてないバイアスが大量に発見される。

成果物: `learner/design_review_feedback.md` に **3 種類のレビューコメント**:

1. **依存方向に違和感がある箇所** — 「mart が staging を直接参照している」「intermediate が他の intermediate を参照している」など
2. **命名が一貫していない箇所** — 「`stg_*_100knock` と `stg_*` が混在」「`mart_daily_*` と `mart_*_daily` の語順揺れ」など
3. **「ここを変えると影響が大きい」と気づいた箇所** — `dbt ls --select +<model>+` で確認した影響範囲

> **重要**: これも open-ended。**指摘の正しさより「指摘できたこと」を評価する**。
> 採点は機械的だが、本来の評価は人間レビュー前提。

## 学べること

- **他者視点で DAG を読む** スキル (実務で最も価値が高いがトレーニングしづらい)
- 依存方向 / 命名 / 影響範囲 の **3 観点** でレビューする型 (汎用的に使える)
- `dbt ls --select +<model>+` で影響範囲を客観評価する技術
- 「指摘の言い方」 = 攻撃ではなく改善提案として書く文体
- 自分のバイアスに気づく (= 自分の DAG にも同じ問題が潜んでいる可能性)

## 前提

- 10-8 完了 (自分の DAG を design_review.md にまとめた経験)
- レビュー対象の DAG が存在 (ペア / 将来の自分 / 6 ヶ月前の自分のいずれか)
- 学習者の成果物配置: `docs/exercises/100-knock/topic-10-integration/learner/design_review_feedback.md`

## 入力データ

なし。レビュー対象の DAG を読んでコメントを書くだけ。

## 課題

### Step 1: ファイル作成

```bash
touch docs/exercises/100-knock/topic-10-integration/learner/design_review_feedback.md
```

### Step 2: 必須セクション 3 つを書く

`design_review_feedback.md` に以下 3 セクションを **必ず** 含める (見出しは H2 = `## ` で):

1. **`## 依存方向`** — 依存方向に違和感がある箇所 (>= 100 文字の本文)
2. **`## 命名`** — 命名が一貫していない箇所 (>= 100 文字の本文)
3. **`## 影響範囲`** — 「ここを変えると影響が大きい」気づき (>= 100 文字の本文)

### Step 3: 各セクションに具体的指摘 1 つ以上

- レビュー対象の model 名 / ファイル名を具体的に挙げる
- 「なぜそれが気になったか」 を 1〜2 文で
- 「どう変えるとよいか」 の改善案を 1 文で (任意)

### Step 4: 採点

```bash
python3 scripts/grader/grade.py --grading-file docs/exercises/100-knock/topic-10-integration/10-9-peer-review.grading.yaml
```

## 評価軸 (人間レビュー前提、CI では検証しない)

| 軸 | 評価ポイント |
|---|---|
| **指摘が具体的か** | 「依存方向が変」 だけでなく、`mart_X が stg_Y を直接 ref していて intermediate を飛ばしている` まで具体的に |
| **改善案があるか** | 指摘だけで終わらず「`int_Y` を挟む案」など改善案を 1 文で示す |
| **影響範囲が客観評価されているか** | 「これは大きく影響しそう」 の感覚ではなく `dbt ls --select +<model>+` のコマンド結果で N model に影響と数値化 |
| **言い方が建設的か** | 「ダメ」「悪い」 ではなく「気になった」「~~ するとよりよさそう」 の文体 |

実務で「コードレビューが上手い人」は **指摘の正しさ + 言い方の建設性** の両方を持っている。本問は前者を機械採点、後者を人間レビュー軸とする。

## ヒント (詰まったら)

- **「将来の自分」レビューの始め方**:
  1. 自分の `design_review.md` を 1 週間後に読み返す (記憶を一旦消す)
  2. 初見の人として読み、「えっ、ここなんで?」を全部メモ
  3. 3 つの観点 (依存方向 / 命名 / 影響範囲) でグルーピング
  4. レビューコメントとして書き起こす
- **「依存方向の違和感」のネタ案**:
  - mart が staging を直接 `ref` (intermediate を経由していない)
  - intermediate が他の intermediate を ref (層を飛び越えた依存)
  - source が複数 staging から ref されている (staging が小さく分割されすぎ)
  - exposure が staging を直接 ref (mart を経由していない、grain が staging のままで使われている)
- **「命名の不一致」のネタ案**:
  - `stg_*_100knock` と `stg_*` の suffix 揺れ
  - `mart_daily_*` と `mart_*_daily` の語順揺れ
  - 集計列が `total_amount` / `sum_amount` / `amount_total` で揺れ
  - PK が `*_id` と `*_pk` と `id` の混在
  - スネークケースとキャメルケースの混在
- **「影響範囲」の客観化**:
  ```bash
  cd dbt && dbt ls --profiles-dir . --select +<model>+
  ```
  上流 + 下流の全 model 数を出して「N 個に影響」 と書く。N >= 5 なら大きい、N >= 10 なら要注意。
- **言い方のテンプレ**:
  - 攻撃: 「~~ がダメ」「なんで ~~ なの」
  - 建設的: 「~~ が気になった」「~~ するとより読みやすそう」「~~ の理由を知りたい (議論したい)」
- **指摘 0 個では PASS しない**: 機械採点で各セクション >= 100 文字なので、必ず 1 つ以上の指摘が必要。何も指摘がない DAG はない (人間が書く限り) ので、「全くダメ」 ではなく「強いて言えば」 のレベルで OK。
- **自分の DAG にも同じ問題があるかも**: 他者を見て指摘した問題の **半分は自分の DAG にも潜んでいる**。レビューコメントを書きながら自分の修正点メモも作るとよい。
