## Step 3: `dbt/models/exercises/07/int_calendar.sql`

```sql
{{ config(materialized='view', schema='intermediate') }}

with bounds as (
    select
        (select min(order_date) from {{ ref('mart_daily_sales') }})       as start_date,
        (select max(order_date) + interval '1 day' from {{ ref('mart_daily_sales') }}) as end_date
),
spine as (
    {{ dbt_utils.date_spine(
        datepart="day",
        start_date="(select start_date from bounds)",
        end_date="(select end_date from bounds)"
    ) }}
)

select date_day::date as calendar_date
from spine
```

**ポイント**:

- `dbt_utils.date_spine` は `date_day` という column 名で行を返す。明示的に `::date` で cast しておくと下流で扱いやすい。
- `bounds` CTE で動的に範囲を決めることで、`mart_daily_sales` の追加・縮小に追随する。リテラル `'2026-01-01'` を直書きしてもよいが、固定値はメンテが面倒。
- `interval '1 day'` を加えるのは date_spine の `end_date` が **半開区間 `[start, end)`** だから。max 日も含めたい場合に必要。

## Step 4: `dbt/models/exercises/07/mart_calendar_sales.sql`

```sql
{{ config(materialized='table', schema='marts') }}

select
    cal.calendar_date,
    coalesce(sales.total_sales_amount, 0)::numeric(14, 2) as total_sales_amount,
    coalesce(sales.order_count, 0)                        as order_count,
    coalesce(sales.customer_count, 0)                     as customer_count
from {{ ref('int_calendar') }} cal
left join {{ ref('mart_daily_sales') }} sales
    on sales.order_date = cal.calendar_date
order by cal.calendar_date
```

**ポイント**:

- LEFT JOIN + COALESCE で欠損日を 0 埋め。「データが無い日」と「売上 0 円の日」を区別したい場合は別途フラグ列 `is_business_day` を追加。
- `materialized='table'` で物質化（BI から頻繁に参照される想定）。

## Step 7: 欠損日確認

```sql
analytics=> SELECT count(*) FROM marts.mart_calendar_sales;
 count
-------
   365
(1 row)

analytics=> SELECT count(*) FROM marts.mart_daily_sales;
 count
-------
   365
(1 row)
```

ダミーデータでは Faker が 365 日全て注文を生成するため、`mart_daily_sales` も `mart_calendar_sales` も同じ 365 行になる。実運用では「日曜は注文ゼロ」など欠損日が発生し、`mart_calendar_sales` の方が行数が多くなる。

人為的に欠損日を作って動作確認したい場合:

```sql
DELETE FROM raw.orders WHERE order_date = '2026-06-15';
```

そのあと `dbt run --select +mart_calendar_sales` で再 build すると、`2026-06-15` の行が `mart_daily_sales` から消える一方、`mart_calendar_sales` には `total_sales_amount = 0` で残ることが確認できる。

## 解説まとめ

- **packages の追加コストはほぼゼロ**。`dbt deps` 一発で `dbt_packages/` 配下に展開される。`dbt_packages/` は `.gitignore` 済みなので、`packages.yml` のみがリポジトリに残る lock 戦略。
- **`date_spine` の典型用途**: 時系列 BI で欠損日埋め / 月次月初日列の生成 / 営業日カレンダーの土台。
- **`dbt-utils` の他 macro 例**:
  - `dbt_utils.generate_surrogate_key(['col1', 'col2'])` — 複数列を MD5 で 1 列にまとめる
  - `dbt_utils.pivot('category', dbt_utils.get_column_values(ref('stg_products'), 'category'))` — 行→列展開
  - `dbt_utils.deduplicate(...)` — window 関数で重複削除
  - `dbt_utils.union_relations([ref('a'), ref('b')])` — schema が違う 2 表を union（不足列は NULL 補完）
- **package selection 戦略**: `dbt-utils` は dbt-labs 公式準パッケージで安定している。それ以外（`dbt-expectations` / `dbt-audit-helper` / `re_data` など）も hub.getdbt.com で探せる。

## 拡張アイデア

- `mart_calendar_sales` を Metabase で時系列折れ線として可視化し、`mart_daily_sales` ベースのグラフと並べて差分（欠損日）を確認
- `dbt_utils.generate_surrogate_key` を `mart_top_rated_products`（Exercise 02）の primary key 統一に応用
- `dbt_utils.pivot` で `mart_product_sales` を `category` でピボットして、カテゴリ別の月次売上比較表を作る
