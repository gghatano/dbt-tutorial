## 推奨マージ手順

```bash
# 1) 順番にレビュー
gh pr view 4   # まず grader 本体
gh pr view 5   # 既存 Exercise の grading
gh pr view 6   # ...

# 2) 順番にマージ (各 PR を develop に取り込む)
#    PR #4 → develop
gh pr merge 4 --merge   # or --squash

#    PR #4 がマージされたら、PR #5 の base が自動的に develop に向き直る
#    GitHub UI で base を develop に変更してからマージ
gh pr edit 5 --base develop
gh pr merge 5 --merge

# ... 以降 #6 〜 #11 も同様

# 3) develop が安定したら main に取り込む
git checkout main
git merge develop
git push origin main
```

または **stack をまとめて 1 PR に rebase** したい場合は、最終ブランチ `feature-100-knock-topic-10` を develop に直接 PR する単一 PR に切り替えても良い。ただしレビュー量が膨大になるので、上記の段階マージを推奨。

## 採点 CI の使い方 (学習者向けクイックスタート)

### Step 1. 解答ブランチを切る

```bash
git checkout -b exercise-06-my-attempt          # 既存 Exercise 06 の場合
git checkout -b exercise-100-knock-1-3-stores   # 100-knock の場合
```

ブランチ名に `exercise-NN[-keyword]` または `exercise-100-knock-T-N[-keyword]` を含める。

### Step 2. 解答を書く

例: Exercise 06 (exposures + dbt docs) なら `dbt/models/exposures/exposures.yml` を作る。

### Step 3. push

```bash
git push origin exercise-06-my-attempt
```

GitHub Actions が自動起動 → Postgres 起動 → ダミーデータ → dbt build → grader → OK / NG を PR コメント or Job Summary に投稿。

### Step 4. ローカル採点 (任意、CI を待たずに)

```bash
set -a; source .env; set +a
python3 scripts/grader/grade.py --exercise 06
# または
python3 scripts/grader/grade.py --exercise 100-knock-1-3-stores
```

## アーキテクチャ図 (採点 CI)

```text
学習者 (ローカル):
  $ git checkout -b exercise-06-my-attempt
  $ vim dbt/models/exposures/exposures.yml
  $ git add . && git commit -m "Exercise 06 attempt"
  $ git push
       │
       ▼
GitHub Actions (.github/workflows/grade.yml):
  1. Checkout
  2. Postgres service container 起動
  3. uv venv + Python deps install (incl. pyyaml)
  4. scripts/ci/bootstrap_schemas.sql で role / schema 作成
  5. scripts/generate_dummy_data.py
  6. scripts/load_raw_data.py
  7. cd dbt && dbt deps && dbt build
  8. python scripts/grader/grade.py --exercise <id from branch name>
       │
       ▼
grader 本体 (Python):
  - find_grading_file() で <id>*.grading.yaml を解決
  - YAML を yaml.safe_load
  - 各 check を順に実行 (9 種類)
    - dbt_command   : dbt CLI 実行 + exit code
    - manifest_*    : target/manifest.json を JSON parse
    - dbt_test_passes : dbt test --select の summary parse
    - sql_assert    : psycopg で SELECT 実行 + 値比較
    - file_exists   : リポジトリ内ファイル存在
    - shell_command : 任意コマンド + stdout 正規表現
    - csv_assert    : CSV の rows / columns / unique / no_nulls
  - GradingResult を組み立てて
    - stdout: 表形式
    - markdown: PR コメント用
    - exit code: 0 (PASS) / 1 (FAIL) by passing_score
       │
       ▼
GitHub Actions:
  - Job Summary に markdown report 表示
  - PR の場合は actions/github-script で comment 投稿
  - exit 1 なら job 失敗 (= PR red)
```

## 振り返り: うまくいったこと / 改善余地

### うまくいった

- **チーム並列**: 4 sub-agent × 5 問の構成で wallclock を 1/4 に短縮
- **stacked PR**: トピック単位でレビュー可能、conflict 最小
- **grader 拡張性**: 9 check 種別に分解、新トピックで必要な check も小さい追加で済む
- **WHY 重視のドキュメント**: 各問の「何を宣言するか」「なぜ重要か」を agent prompt で強制

### 改善余地

- **agent 出力のレビュー**: 4 並列 × 5 問 = 60 ファイルを一度に commit するため、問題ごとの質チェックが甘い。レビューを別 sub-agent に分業すべきだった (時間があれば)
- **CI 実走未検証**: workflow を書いただけで、実際に PR で grader が動くかは未検証。マージ前のテスト必須
- **grading.yaml の検証**: yaml.safe_load + 100 pts 確認だけで、check が「学習者の成果物を正しく検証するか」の semantic な検証はしていない。実際に Ex.06 を解いて 100/100 取れるか試すべき
